# Section 2：我的 BPE 训练与 Tokenizer 实现总结

> 整理日期：2026-09-14。以当前 [cs336_basics/bpe.py](../cs336_basics/bpe.py) 的实际实现为依据，重点记录实现思路、关键变量、执行顺序和容易忘记的细节。本文不是 Section 2 全部实验的完成证明；本次未重新运行训练或测试，也未修改代码。

## 1. 先记住整个设计

**训练是在语料上学习合并规则；编码是在新文本上按规则顺序执行合并；解码是还原字节。**

```text
train_bpe：文件 → 安全分块 → 并行预分词计数 → frequency
          → 建立 pairs 和 pair_word
          → 选最高频 pair → 只更新受影响的 word → 重复
          → vocab + merges

encode：文本 → 分离并保留特殊 token → 普通部分用 PAT 预分词
       → 每个预分词转为单字节序列 → 按最小 rank 合并 → token ID

decode：token ID → bytes → 拼接全部 bytes → UTF-8 字符串
```

这份实现的主要方法可以压缩成五点：

1. **重复文本先聚合**：相同预分词只存一份表示，用频次记录出现次数。
2. **倒排索引定位更新范围**：从一个 pair 找到所有包含它的 word。
3. **受影响的词整体重新计数**：扣除旧表示的全部 pair 贡献，合并后加入新表示的全部贡献。
4. **训练和编码复用同一种合并扫描思路**：从左到右，命中后走两步，避免重叠合并。
5. **编码复用计算结果**：给单个预分词的编码加 LRU 缓存。

## 2. 先分清数据表示

### 2.1 字符、字节、token、ID

| 对象 | 示例 | 含义 |
| --- | --- | --- |
| 原始字符串 | `"abab"` | Python `str`，用于正则预分词 |
| UTF-8 字节串 | `b"abab"` | 字符串编码后的字节 |
| 初始 word | `(b"a", b"b", b"a", b"b")` | 一个预分词的当前 token 序列 |
| 合并后的 word | `(b"ab", b"ab")` | 原始字节不变，token 分组改变 |
| token ID 序列 | `[新token的ID, 新token的ID]` | 模型最终接收的整数序列 |

这里的 `word` 是正则产生的 **pre-token 的表示**，不一定是自然语言中的一个单词，也可能是带前导空格的词、标点或空白。

遍历 `bytes` 得到整数，所以代码用 `bytes([x])` 把一个整数恢复为单字节对象。`bytes(3)` 是三个零字节，和 `bytes([3])` 不一样。

训练使用 `tuple[bytes, ...]`，因为它可哈希，能够作为字典键、集合元素；构造新表示时先用列表 `append`，完成后再转为元组。

### 2.2 必须一直成立的性质

- 合并前后，`b"".join(word)` 不变。
- 合并不能跨越预分词边界，也不能跨越被隔开的特殊 token。
- 普通文本从 256 种单字节出发，因此可以表示 UTF-8 文本中的所有字节。
- 单个 token 的字节不一定能独立解码为合法字符，尤其是中文、emoji。

## 3. train_bpe：参数、变量与返回值

### 3.1 接口

| 参数 / 返回值 | 含义 |
| --- | --- |
| `input_path` | 训练语料文件路径 |
| `vocab_size` | 目标词表总大小，包含基础字节和特殊 token |
| `special_tokens` | 需要保留为独立 token 的字符串列表 |
| 返回的 `vocab` | `dict[int, bytes]`，ID 到 token 字节串的映射 |
| 返回的 `merges` | `list[tuple[bytes, bytes]]`，按训练先后排列的合并规则 |

基础字节占 ID `0～255`，特殊 token 从 `256` 开始加入，`index = 256 + len(special_tokens)` 指向下一个新 ID。在输入有效、候选 pair 足够的前提下，合并轮数为：

```text
vocab_size - 256 - len(special_tokens)
```

例如目标 10,000、一个特殊 token，需要 9,743 次合并。

### 3.2 三个核心结构

| 变量 | 键 → 值 | 解决的问题 |
| --- | --- | --- |
| `frequency` | 当前 word 元组 → 语料出现次数 | 这个预分词出现了多少次？ |
| `pairs` | 相邻 token 对 → 加权出现次数 | 哪个 pair 最常见？ |
| `pair_word` | 相邻 token 对 → 包含它的 word 集合 | 合并这个 pair 会影响哪些词？ |

其他变量：`max_pair` 是本轮选中的 pair；`count` 是当前受影响词的频次；`new_word` 是合并后的表示；`i` 是扫描位置；`n` 是旧表示的 token 数。

最关键的区别：**`pairs` 记录次数，`pair_word` 记录成员关系。**

例如 `(b"a", b"a", b"a", b"a")` 出现 5 次：

- `(b"a", b"a")` 有 3 个相邻位置，因此向 `pairs` 贡献 `3 × 5 = 15`。
- `pair_word[(b"a", b"a")]` 只需要保存这个 word 一次。
- 所以 `pair_word` 的值用 `set`，避免同一个词因重复 pair 被处理多次。

## 4. 训练第一阶段：分块、预分词、聚合

### 4.1 find_chunk_boundaries

参数 `file` 是二进制文件对象，`desired_num_chunks` 是期望块数，`split_special_token` 是用于定位边界的字节串；返回值是排序、去重后的字节偏移列表。

按源码顺序理解：

1. `seek` 到文件尾，用 `tell()` 获取字节大小，然后回到文件头。
2. 按文件大小均匀估计分块位置。
3. 对每个内部位置向后按 4096 字节读取，寻找分隔特殊 token。
4. 找到后将边界移到特殊 token 的起点；读到 EOF 则移到文件末尾。
5. 排序、去重；相邻边界组成 `[start, end)` 区间。

这样做是为了让各块可以独立预分词，避免随便在普通词中间切一刀。当前训练写死使用 `b"<|endoftext|>"` 作为分隔符，并固定开 6 个进程；这依赖当前语料的约定。

### 4.2 count_chunk

参数 `input_path` 是路径，`start/end` 是字节区间，`special_tokens` 是需排除的特殊字符串；返回当前块的 `Counter`。

执行顺序：

1. 子进程自己打开文件，`seek(start)` 后读取 `end - start` 字节。
2. 解码成字符串。
3. 对特殊 token 做 `re.escape`，拼成正则分支，再用不带捕获组的 `re.split` 把它们切掉。
4. 对每个普通片段，用 `re.finditer(PAT, part)` 找出预分词。
5. `.group()` 取字符串，`.encode("utf-8")` 转字节，再拆成单字节元组。
6. `counter[word] += 1`，返回局部频次。

训练时“切掉”特殊 token 是指不让它参与普通 pair 统计；它已在初始化时被加入词表。切开的两侧分别处理，不能重新拼接，否则会产生跨边界 pair。

`PAT` 使用的是第三方 `regex`（别名 `re`），包括缩写、字母、数字、标点和空白等分支，`\p{L}`、`\p{N}` 依赖这个库。训练和编码必须保持同一套规则；不能随意 `strip()` 丢掉空格或换行。

### 4.3 主进程汇总

`task` 保存各块的参数元组，`Pool.starmap(count_chunk, task)` 将元组展开为函数参数，结果 `counters` 是各任务返回的 Counter 列表。

主进程逐个执行 `frequency.update(counter)`，把同一个 word 在各块中的频次相加。`update()` 原地修改并返回 `None`。

传路径和偏移、让子进程重新打开文件，便于进程间序列化；普通全局变量不会自动在进程之间同步。这里只并行预分词计数，后面的逐轮 BPE 合并仍在主进程中串行执行。

## 5. 训练第二阶段：选择 pair 并增量更新

### 5.1 建立初始统计

遍历每个唯一 word 的所有相邻位置：

- `pairs[pair] += frequency[word]`：每出现一个位置，就加上该词频次。
- `pair_word[pair].add(word)`：登记包含关系。

长度为 1 的 word 没有相邻 pair，直接跳过。之后 `frequency` 中保存的是不断变化的当前表示，不再一直是初始单字节表示。

### 5.2 选择规则

`max(pairs, key=lambda pair: (pairs[pair], pair))` 的比较键有两级：

1. 优先选择频次最大的 pair。
2. 同频时，选择 pair 元组字典序最大的那个。

这里比较的是 `(left_bytes, right_bytes)`，先比较左边，再比较右边，不能擅自改成比较拼接后的字节串。

选中后，把左右字节拼接存入 `vocab[index]`，并将 `max_pair` 追加到 `merges`。规则列表的顺序就是将来编码时的优先级。

### 5.3 我的更新策略：只碰受影响的词，但重算该词全部 pair

对 `pair_word[max_pair].copy()` 中的每一个旧 word，依次执行：

1. 保存 `count = frequency[word]`。
2. 遍历旧 word 的全部相邻位置，从 `pairs` 中扣除各自的 `count`。
3. 扫描旧 word，完成本轮选中 pair 的所有非重叠合并，得到 `new_word`。
4. 将新表示写入 `frequency`，删除旧表示。
5. 遍历新 word 的全部相邻位置，向 `pairs` 加回各自的 `count`。
6. 从旧 pair 的倒排集合中移除旧 word，并删除频次为零的候选 pair。
7. 向新 pair 的倒排集合中加入 `new_word`。

最后删除本轮选中的 `max_pair`，递增 `index`，进入下一轮。

**核心公式：全局新计数 = 全局旧计数 − 旧 word 的贡献 + 新 word 的贡献。**

这不是每轮重扫全语料，也不是仅维护合并点左右两个邻居；它在两个层次上做了取舍：先用倒排索引缩小到受影响的词，再对这些词整体重算，减少边界分支和漏计风险。

`.copy()` 不能随意删除：循环体也会修改 `pair_word[max_pair]` 对应的集合，直接遍历原集合可能触发“遍历时集合大小改变”。`discard()`、`pop(..., None)` 则允许重复清理时目标已经不存在。

### 5.4 手算一轮

假设聚合后的语料为：

```text
(a, b, a, b) 出现 3 次
(a, b, a)    出现 2 次
```

为简洁省略 `b"..."`，其中每个元素仍表示 bytes。初始计数：

```text
(a, b)：2 × 3 + 1 × 2 = 8
(b, a)：1 × 3 + 1 × 2 = 5
```

选中 `(a, b)` 后：

| 旧 word | 新 word | 频次 | 新 pair 贡献 |
| --- | --- | ---: | --- |
| `(a, b, a, b)` | `(ab, ab)` | 3 | `(ab, ab)` 加 3 |
| `(a, b, a)` | `(ab, a)` | 2 | `(ab, a)` 加 2 |

旧 `(a,b)` 和 `(b,a)` 的贡献全部被扣掉，新的候选是 `(ab,ab)` 与 `(ab,a)`。词的出现次数没有改变，只改变了内部切法。

### 5.5 非重叠合并为什么需要 i += 2

训练和编码都采用以下扫描逻辑：

- 当前相邻 pair 未命中：把 `word[i]` 放入结果，`i += 1`。
- 命中：把 `word[i] + word[i+1]` 放入结果，`i += 2`。
- 扫描结束后，如果 `i == n - 1`，补上最后一个未处理 token。

例如 `aaaa` 合并 `aa` 得到 `[aa, aa]`；`aaa` 得到 `[aa, a]`。统计时允许相邻位置重叠，因此 `aaaa` 中有 3 个 `aa`，但本轮实际只能做 2 次非重叠替换。**pair 计数不等于本轮替换次数。**

## 6. Tokenizer：参数、状态与返回值

构造参数：`vocab` 是训练词表，`merges` 是有序规则，`special_tokens` 是需要整体识别的特殊字符串，默认 `None`。`__init__` 完成初始化，不返回编码结果。

| 成员 | 含义 |
| --- | --- |
| `self.vocab` | ID → bytes，供解码使用 |
| `self.merges` | 有序的训练合并规则 |
| `self.max` | 规则总数，也用作“无规则”的 rank 哨兵 |
| `self.reverse_vocab` | bytes → ID，供编码最终查询 |
| `self.reverse_merge` | pair → rank，rank 是规则在列表中的下标 |
| `self.special_tokens` | 特殊字符串列表 |

`self.max` 不是最大 token ID。合法 rank 范围为 `0` 到 `len(merges)-1`，因此用 `len(merges)` 表示未找到规则，比所有合法 rank 都大。

## 7. encode_word：按 rank 重放规则，并缓存结果

参数 `pre_token: str` 是一个普通预分词；返回值 `list[int]` 是它编码后的 token ID 列表。

按照源码顺序：

1. 将 `pre_token` 编码为 UTF-8，再拆成单字节列表 `word`。
2. 只要 token 数大于 1，就枚举当前所有相邻 pair。
3. 构造 `ranks`：当前 pair → 训练 rank。同一 pair 重复出现只存一个键即可，因为这里只选择规则，不统计次数。
4. `min(ranks, key=ranks.get)` 选最小 rank，即训练时最早学到的可用规则。
5. 如果最小值也是 `self.max`，说明当前没有任何合法合并，退出。
6. 否则按从左到右、非重叠的方式，把这一 pair 的所有出现合并。
7. 回到循环开头，重新计算新序列的相邻 pair。
8. 最后用 `reverse_vocab` 将每个 bytes token 转为 ID。

**不能在新文本中重新选最高频 pair，也不能直接贪心寻找词表里最长的字符串。当前算法的依据是训练规则的 rank。**

例如规则依次为 `(a,b)`、`(ab,a)`，输入 `aba`：先从 `[a,b,a]` 合并成 `[ab,a]`，再合并成 `[aba]`。每轮都必须重新看相邻关系，因为上一轮可能创造下一条规则的输入。

### 7.1 LRU 缓存的作用

`@lru_cache(maxsize=100_000)` 记住已经编码过的预分词。重复遇到同一个字符串时，可以直接拿到 ID 列表，省掉重复合并。

- 缓存适合这里，是因为同一 Tokenizer 配置下，同一个 pre-token 的结果确定。
- 上限是 100,000 个缓存条目，不是 100,000 字节；长字符串及结果列表仍可能占用较多内存。
- 方法缓存的键包含 `self` 和参数；不同实例不会仅因字符串相同而共用结果，但它们使用同一个装饰器缓存容量。
- 缓存返回的是同一个列表对象。当前 `encode` 用 `extend` 读取结果，不修改该列表；外部若直接修改 `encode_word()` 的返回值，会污染以后命中的结果。
- 使用期间应保持词表和规则稳定，否则已有缓存与反向映射可能失效。

## 8. encode：特殊 token 和普通文本分开处理

参数 `text: str` 是完整输入；返回 `list[int]`。局部 `tokens` 是累计的输出 ID 列表，`parts` 是切分后的文本片段。

没有特殊 token 时，直接执行 `PAT` 预分词，逐个调用 `encode_word`，把结果 `extend` 到输出。

有特殊 token 时：

1. 按字符串长度降序排列特殊 token，同一起点优先识别较长者。
2. 用 `re.escape` 处理正则元字符，再用 `|` 连接。
3. 使用 `re.split(f"({patterns})", text)`；括号是捕获组，让匹配到的特殊 token 也保留在结果中。
4. 特殊片段直接查 `reverse_vocab`，`append` 一个 ID。
5. 普通片段再经 `PAT` 和 `encode_word`，`extend` 多个 ID。

训练与编码在这里故意不同：训练切分时不保留特殊字符串参与统计；编码切分时必须保留，以便输出它的 ID。切分后可能有空串，普通正则在空串上不产生 token，无需删除邻近空白。

## 9. decode、encode_iterable 和 from_files

### 9.1 decode：先合并 bytes，再解码

参数 `ids: list[int]` 是 ID 序列；返回 `str`。`b_text` 累积字节串，`text` 是最终字符串。

代码逐个查 `vocab[i]` 拼接字节，最后统一执行 UTF-8 解码，并指定 `errors="replace"`。非法字节序列会显示为替换字符 `�`。

不能逐 token 解码后再拼字符串：一个中文字符的 UTF-8 字节可能分布在多个 token 中，分开解码会破坏本来完整的字符。

当前重复执行 `b_text += ...`，长序列可能产生较多字节复制；后续若优化，可考虑先收集字节再一次 `join`。这是性能建议，不改变算法含义。

### 9.2 encode_iterable：按输入片段惰性输出

参数 `iterable: Iterable[str]` 可以是文件迭代器等；返回 `Iterator[int]`。函数内部的 `yield token_id` 逐个产出整数，而不是返回整个文件的列表。

执行方式是：取一段 `text` → `encode(text)` 得到该段列表 → 逐个 `yield` → 再处理下一段。

所以它避免一次保存整个输入的编码结果，但仍需容纳当前片段及其 ID 列表，加上词表与缓存。它不是“任何输入下都固定占用极少内存”。

**当前实现把每个输入片段视为独立编码单位，没有跨片段缓冲。** 若连续文本被切成 `"hel"` 和 `"lo"`，分别编码可能不同于整体编码 `"hello"`；特殊 token 跨片段也无法整体识别。使用时要明确片段边界的语义，不能假定任意分块都与一次性编码一致。

### 9.3 from_files：恢复自己的 JSON 格式

`cls` 是类本身；`filepath` 是单个 JSON 文件路径；签名还有 `special_tokens` 可选参数。返回 `cls(...)` 创建的 Tokenizer 实例。

当前读取格式可以用下面的小片段理解（仅演示结构，并非完整基础词表）：

```json
{
  "vocab": {"97": "61", "98": "62", "256": "6162"},
  "merges": [["61", "62"]],
  "special_tokens": []
}
```

代码先 `json.load`，再把词表的字符串 ID 用 `int()` 还原，把十六进制值用 `bytes.fromhex()` 还原；合并规则也恢复为 bytes pair，并保持列表顺序，最后调用构造函数。

十六进制可以无损表示任意 token 字节，不要求每个 token 都是合法 UTF-8。当前是单文件自定义格式，不能直接等同于测试 fixture 的 GPT-2 格式或其他文档中的双文件接口。

注意：函数内 `special_tokens = data.get("special_tokens", None)` 会覆盖调用方传入的同名参数，所以当前实际以文件内容为准，文件缺少字段时得到 `None`。

## 10. 当前实现的关键边界与后续注意点

以下来自静态阅读；把它们与上面已经实现的算法区分开，避免以后把假设当成保证。

| 位置 | 当前行为 / 需要记住的限制 |
| --- | --- |
| `count_chunk` 的 `None` 分支 | `parts = chunk` 得到字符串，后续会逐字符循环，而非把整块作为一个片段；且 `train_bpe` 自身不支持传 `None` |
| `count_chunk` 的空列表 | 空列表会构造空正则，导致按空匹配切分，改变正常预分词；不能认为和 `encode` 的空列表处理等价 |
| 训练的特殊 token 匹配 | 没有像 `encode` 那样按长度降序排序；有前缀重叠时，分支顺序可能影响切分 |
| 分块搜索 | 4096 字节窗口没有重叠，可能漏掉跨窗口的分隔符；可能造成分块不均匀、并行度降低 |
| 固定分隔符 | 只有它确实是允许独立处理的边界时，才能保证分块不改变语义；没有分隔符时可能退化为一个大块 |
| `errors="ignore"` | 读取时会丢弃非法 UTF-8 字节，不能用它替代边界正确性验证 |
| 候选耗尽 | `while` 只看 `index < vocab_size`，`pairs` 提前为空时 `max()` 会报错 |
| 目标大小 | 小于基础词表加特殊 token 数时，当前不会拒绝输入，返回词表会超过目标大小 |
| `frequency[new_word] = count` | 这里是赋值而非累加；当前从唯一字节串开始、统一执行确定性合并，同字节串只有一份当前表示，依赖这一性质。推广到其他状态合并算法时需重新分析键冲突 |
| 特殊 token 词表项 | `Tokenizer.__init__` 不会自动补入缺失的特殊 token；编码遇到缺失项会查表失败 |
| 词表与规则一致性 | 合并结果应在词表中；重复 bytes 值会在反向词表中覆盖 ID，特殊列表也应避免重复、空串等含糊输入 |
| `reverse_merge` | 使用 `defaultdict` 的下标查询，会把未见 pair 以哨兵 rank 写入字典，长期使用时可能增长 |
| `encode_iterable` | 不保证任意字符串切块与整段编码产生相同 ID，尤其要考虑预分词和特殊 token 跨块 |
| `from_files` | 使用单 JSON 格式，且调用方传入的特殊 token 参数被文件内容覆盖 |

## 11. 如何记住并验证这套算法

### 11.1 训练中最有用的三个检查

1. 每轮开始时，`pairs[p]` 应等于所有当前 word 中该 pair 的位置数乘以词频，再求和。
2. `pair_word[p]` 应恰好包含当前仍有该 pair 的 word；不存在的 pair 可以留下空集合，但不能留有失效的旧 word。
3. 每个词合并前后字节拼接不变，且当前词频总和保持不变。

如果以后怀疑增量更新错了，可以在极小语料上手动全量重算 pair 计数，与维护的 `pairs` 比较。这比直接在大语料上观察最终词表更容易定位哪一轮出错。

### 11.2 复习用小例子

| 例子 | 应重点检查 |
| --- | --- |
| `aaaa`、`aaa` | 重叠计数与非重叠替换、最后一个 token 的补回 |
| 两个 pair 同频 | 是否选 pair 元组字典序最大的 |
| 同一个词重复多次 | pair 是否按词频加权，而倒排集合只存一次 |
| 中文或 emoji 往返 | 是否先拼全部字节再解码 |
| 前缀重叠的特殊 token | 是否完整保留较长匹配及邻近空白 |
| `"hel"`、`"lo"` 两段 | 独立片段编码和整段编码的区别 |
| 保存后重新加载 | ID 类型、bytes 内容、merges 顺序是否完整还原 |

当前 [tests/adapters.py](../tests/adapters.py) 已将 `run_train_bpe` 和 `get_tokenizer` 接到这份实现。以后可以在项目根目录运行：

```bash
uv run pytest tests/test_train_bpe.py tests/test_tokenizer.py
```

这是一条复测命令，不代表本次已通过。训练测试比较参考合并规则、词表及特殊 token 行为，也包含速度检查；Tokenizer 测试涵盖往返、参考 ID、特殊 token、空白、流式等情况。**能解码还原原文只是必要检查，错误的切法也可能还原原文，因此还要比较 ID 序列。**

### 11.3 性能方面已经留下的线索

已有的 [BPE 训练耗时记录](../md/bpe训练耗时记录.md) 记录了 2026-09-11 的一次运行：约 2.23 GB TinyStories 语料、6 个进程、10,000 词表，总耗时约 119.246 秒；预分词相关阶段占约 77.76%，合并阶段约 26.349 秒，其中 `max(pairs, ...)` 占约 94.80%。这是历史记录，不是本次复测或当前代码的性能保证。

它说明这套倒排索引已经减少了合并更新的工作，但每轮 `max` 仍扫描全部候选。以后若优化，可以分别考虑预分词吞吐量和候选最大值查询；不必先把已经清晰的词级增量更新改得更复杂。

## 12. 隔一段时间回来，先看这十句话

1. 我的 `word` 是一个预分词的当前 bytes token 元组，不是原始字符串。
2. `frequency` 压缩重复词，`pairs` 保存加权次数，`pair_word` 定位受影响的词。
3. 每轮训练选最高频 pair，同频选 pair 字典序最大的。
4. 更新顺序是“扣旧贡献 → 合并 → 加新贡献 → 更新倒排索引”。
5. 同一个 pair 在一个词中能出现多次，但这个词只处理一次。
6. 扫描命中走两步，未命中走一步，最后可能需要补一个 token。
7. 编码选最小训练 rank，不重新统计频次。
8. 特殊 token 在训练统计中隔开，在编码输出中保留。
9. 解码先拼字节；流式输出要额外考虑片段边界；缓存要求配置稳定。
10. 想验证正确性，除了文本往返，还要检查计数不变量、合并顺序和最终 ID。
