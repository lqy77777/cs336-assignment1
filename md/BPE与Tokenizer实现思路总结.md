# BPE 与 Tokenizer 实现思路总结

本文结合当前 [bpe.py](../cs336_basics/bpe.py) 和实现过程中的讨论，记录核心设计、数据结构、常见错误及尚需注意的边界。本文是代码学习总结，不代表已经通过全部测试；本次只整理文档，没有修改代码。

## 1. 整体思路：学习规则与使用规则

```text
训练语料
  → 分块 → 并行预分词与计数 → 汇总频次
  → 统计相邻 pair → 反复选择并合并
  → vocab + merges

输入文本
  → 识别特殊 token → 普通文本预分词
  → UTF-8 字节 → 按 merges 的优先级合并
  → 查询 token ID

token ID 序列
  → 查询字节串 → 拼接全部字节 → UTF-8 解码
```

最重要的区别：**训练根据频次学习规则；编码根据已经学到的规则执行合并。** 编码时不重新训练，也不根据当前文本中的频次决定优先级。

| 阶段 | 决策依据 | 输出 |
| --- | --- | --- |
| BPE 训练 | 最高 pair 频次，同频时按要求选择字典序最大的 pair | 词表与有序合并规则 |
| 文本编码 | 当前可用 pair 中最小的训练 rank | token ID 列表 |
| 文本解码 | 词表中的 ID 到字节映射 | 字符串 |

## 2. 字节级表示：让所有文本使用同一套基础单位

### 2.1 str、bytes、token 序列不是同一种对象

| 表示 | 示例 | 长度含义 |
| --- | --- | --- |
| `str` | `"你好"` | Unicode 字符数 |
| `bytes` | `"你好".encode("utf-8")` | 字节数，此例为 6 |
| token 序列 | `(b"h", b"e", b"l", b"l", b"o")` | 当前 token 数 |
| ID 序列 | `[某个ID, 另一个ID]` | 当前 token 数 |

合并改变的是 token 序列的分组，不能改变它拼接后的原始字节。

```text
(b"a", b"b", b"a", b"b")
            ↓
(b"ab", b"ab")
```

这两个序列的 token 数分别为 4 和 2，但拼接后都是 `b"abab"`。

### 2.2 为什么写 bytes([x])

遍历 `bytes` 得到的是 0–255 的整数。`bytes([x])` 将该整数转换成一个单字节对象。

注意 `bytes(3)` 的含义是创建三个零字节，不是创建数值为 3 的一个字节。二者不能混用。

### 2.3 为什么训练中的 word 使用 tuple

`frequency` 的键要表示整个预分词的当前 token 序列。元组不可变，且其中的 `bytes` 也可哈希，因此可以作为字典键、集合元素；列表不可以。

合并时暂时使用列表方便 `append()`，完成后转换回元组，是合理的设计。

## 3. 预分词：先划定允许合并的范围

你使用第三方 `regex` 库，并取别名 `re`。`PAT` 中的 `\p{L}`、`\p{N}` 需要该库，不能直接用标准库 `re` 替代。

处理普通文本时，`finditer()` 逐个返回匹配对象；`.group()` 取出匹配到的字符串，再编码成 UTF-8 字节。

关键原则：

- 保留空格、换行和前导空格，它们都是原文的一部分。
- 每个预分词内部独立执行 BPE，不跨预分词边界合并。
- 训练与编码必须使用一致的预分词规则。
- 不要用 `strip()` 简化边界，否则可能改变文本和 ID 序列。

## 4. 并行预分词：独立处理，最后汇总

### 4.1 每个任务的输入与返回值

工作函数 `count_chunk(input_path, start, end, special_tokens)`：

- `input_path`：文件路径。
- `start`、`end`：字节区间 `[start, end)`。
- `special_tokens`：应排除在普通训练统计之外的特殊字符串。
- 返回值：当前分块的局部 `Counter`。

每个进程自己打开文件，定位后只读取自己的分块，独立预分词并计数。

### 4.2 为什么传路径，不传文件对象

`BinaryIO` 可以作为普通函数参数。限制来自进程池：任务参数要经过序列化才能传给子进程，而打开的文件对象不能通过普通 pickle 任务传输。

字符串路径和整数偏移可以传输，子进程据此重新打开文件即可。

### 4.3 为什么局部 Counter 必须返回

普通全局变量不自动跨进程共享。子进程修改自己的全局计数器，不会自动改变主进程中的计数器；工作进程复用时，全局计数还可能残留到下个任务。

因此每次任务创建局部计数器，完成后返回。`Pool.starmap()` 返回的是 **`list[Counter]`**，主进程必须逐个累加。

在下面片段中，`counters` 是各任务返回值的列表，`frequency` 是主进程的总计数器。`update()` 原地累加，返回 `None`。

```python
frequency = Counter()
for counter in counters:
    frequency.update(counter)
```

第一行创建空计数器；第二行取出一个局部结果；第三行累加其中的次数。

不能直接 `frequency.update(counters)`，那会尝试把各个 Counter 对象当作待计数元素。也不能写 `frequency = frequency.update(counter)`，因为这会把变量变成 `None`。

### 4.4 分块与多进程的边界

- 分块应落在允许独立处理的边界，例如语料中约定的文档分隔特殊 token。
- 边界去重后可能少于进程数；一个任务不能自动分配给多个进程共同执行。
- 当前 4096 字节窗口搜索可能漏掉横跨两个窗口的特殊 token，可通过保留窗口尾部重叠改进。
- `errors="ignore"` 会丢弃非法字节，不能用它证明切分正确。
- 真正启动训练的脚本调用应位于 `if __name__ == "__main__":` 下。
- 多进程有启动、传输和内存开销，不能直接假设 6 个进程就是 6 倍加速。

## 5. 三个核心数据结构

| 变量 | 保存内容 | 作用 |
| --- | --- | --- |
| `frequency` | 当前预分词 token 元组 → 出现次数 | 将重复预分词压缩为一条记录 |
| `pairs` | 相邻 token 对 → 全语料加权频次 | 选择最高频 pair |
| `pair_word` | 相邻 token 对 → 包含它的预分词元组集合 | 找到本轮需要更新的预分词 |

### 5.1 加权频次

如果 `aaaa` 出现 5 次，它含有三个相邻 `(a,a)`，对全局 pair 频次的贡献是 `3 × 5 = 15`。

但 `pair_word[(a,a)]` 中只需要记录一次这个 word，因此使用 `set`。**计数需要保留重复出现位置，倒排索引只记录哪些 word 受影响。**

### 5.2 倒排索引的意义

选出一个 pair 后，只有包含它的 word 需要改变。`pair_word` 避免每轮扫描所有预分词来判断谁受影响。

你遍历 `pair_word[max_pair].copy()`，是为了在更新原集合时仍能安全遍历该轮的旧成员。`discard()` 删除不存在的成员也不会报错。

## 6. 合并更新：先扣旧贡献，再加新贡献

对每个受影响的 word，当前实现的核心步骤是：

1. 记录旧 word 的频次 `count`。
2. 遍历全部旧相邻 pair，逐个扣减 `count`。
3. 从左到右生成合并后的 `new_word`。
4. 更新 `frequency` 中旧、新序列的记录。
5. 遍历全部新相邻 pair，逐个增加 `count`。
6. 在倒排索引中移除旧 word，加入新 word。
7. 清理频次为零的候选。

### 6.1 为什么扣旧 pair 必须独立扫描

合并 `aaaa` 中的 `(a,a)` 时，真正执行两次非重叠合并，但旧序列有三个相邻 pair。

如果把扣减放在会 `i += 2` 的合并扫描中，就会漏掉中间那个 pair。

因此：**统计旧相邻关系要遍历每个位置；执行合并要跳过已消费的两个 token。**

### 6.2 扫描指针的规则

- 不匹配：复制当前 token，前进 1。
- 匹配：加入两个 token 拼接的结果，前进 2。
- 循环结束若剩一个 token，将它补到末尾。
- 扣减旧 pair 的循环若也使用 `i`，必须在合并扫描前重新设置 `i = 0`。

曾经出现的问题是：前面的 `for i ...` 覆盖了 `i`，导致合并从尾部开始，丢掉前面的字节。

### 6.3 候选清理与退出

`Counter` 不会自动删除零频次键。它们虽然在存在正频次候选时不会胜出，但会增加扫描开销，并影响基于容器是否为空的停止逻辑。

只删除 `max_pair` 不够：合并也可能让它的旧邻接 pair 消失。

通用实现应同时满足“词表未满”和“还有候选”才继续训练。当前代码只检查 `index < vocab_size`，依赖语料始终有足够可合并内容；短文本或空语料仍可能触发 `max()` 空输入错误。

### 6.4 每轮应保持的约束

- 每个新 word 拼接后的字节与旧 word 完全一致。
- 全局 pair 计数等于各 word 的相邻出现次数乘其频次之和。
- `pair_word[pair]` 指向当前确实包含该 pair 的 word。
- `merges` 记录两个旧 token，`vocab[index]` 记录它们拼接后的新 token。
- 新 ID 从下一个可用位置递增；边界使用 `< vocab_size`。

## 7. 编码：训练 rank 替代频次

`Tokenizer` 中的关键映射：

| 属性 | 映射方向 |
| --- | --- |
| `self.vocab` | `ID → bytes` |
| `self.reverse_vocab` | `bytes → ID` |
| `self.reverse_merge` | `pair → rank` |

训练列表的索引就是 rank，越小越优先。编码一个预分词时反复选择当前相邻 pair 中 rank 最小者，合并后继续，直到没有规则可用。

当前使用 `self.max = len(self.merges)` 作为未出现规则的哨兵值，因为合法 rank 范围是 `0` 到 `len(merges)-1`。

关键写法区别：

- `min(ranks)` 比较的是字典的键，即 pair 本身。
- `min(ranks, key=ranks.get)` 才按对应 rank 比较。
- `while len(word) > 1` 避免单 token 或空序列对空候选调用 `min()`。

例如，若 `(b"b", b"c")` 的 rank 为 0，`(b"a", b"b")` 的 rank 为 1，则 `abc` 应变成 `[a,bc]`，而不是 `[ab,c]`。

## 8. 缓存：重复预分词只合并一次

`@lru_cache(maxsize=100_000)` 缓存 `encode_word()` 的返回值，命中后不再执行函数体。

- 缓存键包含 `self` 和完整预分词字符串。
- `"hello"` 与 `" hello"` 不相同，不能去掉空格后共用缓存。
- 容量是十万条记录，不是十万字节。
- 多个实例共用装饰器缓存的容量，但因键包含 `self`，不会直接混用结果。
- 缓存会保留参数与返回值的引用，直到淘汰或清理。
- 词表或合并规则变化后需要清理旧缓存。

当前缓存返回 `list[int]`。`encode()` 只用 `extend()` 读取它，并未修改缓存结果；但其他调用者若修改返回列表，后续命中结果会被污染。建议返回不可变的 `tuple[int, ...]`。

另外，当前 `reverse_merge` 是 `defaultdict`，查询不存在的 pair 会将哨兵值插入字典。长时间编码会积累额外记录；普通字典配合 `.get(pair, self.max)` 可以避免查询产生写入。这与 LRU 缓存是两套独立的内存来源。

## 9. 特殊 token：先识别，再处理普通文本

训练时，特殊 token 不参与普通 pair 学习；编码时，特殊 token 必须保留并变成一个整体 ID。

当前 `encode()` 中做对的关键步骤：

1. `None` 或空列表时，直接预分词整个输入。
2. 特殊 token 从长到短排序。
3. 通过 `re.escape()` 转义正则字符。
4. 构造正则捕获组，让 `re.split()` 保留特殊 token。
5. 特殊字符串编码为 `bytes` 后查询反向词表。
6. 普通片段执行 `PAT` 和缓存的 BPE 合并。

曾经容易混淆的地方：

- `re.split((patterns), text)` 中的括号属于 Python 表达式，不能保留分隔符。
- `re.split(f"({patterns})", text)` 的括号才属于正则捕获组。
- 排序必须发生在构造正则时；在 `part in sorted(...)` 中排序不会影响已经完成的切分。
- `parts = text` 会逐字符遍历；一个完整片段应表示为 `[text]`。
- `reverse_vocab` 的键是 `bytes`，不是特殊 token 的 `str`。

当前初始化尚未把缺失的用户特殊 token 追加到词表，因此仍依赖它们已经存在。通用接口需要补充该行为，避免编码时 `KeyError`。

## 10. 解码：先拼全部字节，再处理 Unicode

一个 token 的字节不保证能独立解码为字符。

```text
b"\xc3" 单独解码：不完整
b"\xc3\xa9" 一起解码：é
```

所以应先查词表并拼接字节，再使用 `decode("utf-8", errors="replace")`。当前代码已经加入替换模式。

`errors="replace"` 按作业要求将无法解码的字节替换成 `�`，这对测试中单独执行 `decode([id])` 的情况尤其重要。

不能对每个 token 先解码再拼字符串，即使单独解码时也设置替换模式，仍可能破坏原本可以一起还原的 Unicode 字符。

性能建议：当前循环中不断执行 `b_text += ...`，会反复构造不可变字节串。可以使用 `b"".join(...)` 一次拼接，减少重复复制。

## 11. 流式编码：惰性输出不等于边界正确

当前 `encode_iterable()` 逐个编码输入字符串，再逐个 `yield` ID；没有在函数内部累积整个文件的所有 ID。

- `yield token_id` 每次产生一个整数。
- `yield from self.encode(text)` 可以简写内部循环。
- `yield self.encode(text)` 每次产生整个列表，不符合 `Iterator[int]`。
- 无需额外定义内层生成器再返回，外层直接使用 `yield` 即可。

但当前实现独立编码每个输入片段。`["hel", "lo"]` 不保证得到与 `"hello"` 一次编码相同的 ID，跨片段特殊 token 也有同样问题。

因此该实现要求输入边界适合独立编码。若要支持任意连续片段，需要缓冲不能确定的尾部，在安全边界输出结果。文件按行测试通过，不等于所有字符串分块策略都正确。

生成器仍会临时保存当前 `encode(text)` 的结果，内存上限受当前片段大小和缓存影响；不能无条件声称绝对常量内存。

## 12. 文件加载：序列化必须可逆

当前 `from_files()` 是类方法，从一个 JSON 文件加载词表和规则：

- 词表中的 ID 从 JSON 字符串转换回整数。
- token 的十六进制字符串通过 `bytes.fromhex()` 恢复字节。
- 合并列表逐项恢复为两个 `bytes` 的元组，保留顺序。
- 最后使用 `cls(...)` 返回实例。

十六进制表示能保存任意字节，不要求单个 token 是合法 UTF-8 字符串。

当前需要明确的约定：

1. 加载格式必须与保存格式一致；目前使用单个 JSON，与作业推荐的两个路径接口不同，调用方需要配套。
2. 当前 `special_tokens = data.get("special_tokens", None)` 会覆盖调用者传入的参数。应明确优先使用参数还是文件内容；如果希望调用者可覆盖文件设置，不能无条件赋值。
3. 当前 `self.vocab = vocab` 直接持有外部字典；若以后追加 token，应考虑是否先复制，避免意外修改调用者数据。

## 13. 性能分析带来的优化方向

之前一次全量 TinyStories 运行使用 6 个进程，结果记录在 [训练耗时文档](bpe训练耗时记录.md)：

| 阶段 | 当次耗时 |
| --- | ---: |
| 并行读取、预分词、局部计数及传输 | 92.72 秒 |
| BPE 合并 | 26.35 秒 |
| 其中选择最高频 pair | 24.98 秒 |
| 总计 | 119.25 秒 |

这份测量属于当时的代码和运行环境，不是当前版本每次运行的保证，也没有串行对照来计算加速倍数。

值得考虑的优化：

1. 训练时先统计完整预分词字节串，再对每个不同预分词拆一次单字节 token，减少重复对象构造。
2. 缓存 256 个单字节对象，避免反复创建相同对象。
3. 训练阶段用最大堆及过期记录检查替代每轮全扫描 `max()`，但必须保留同频时的字典序规则。
4. 编码阶段使用当前的 LRU 缓存，并查看命中率。
5. 避免热路径中的重复正则构造和无必要排序，可在初始化时准备。
6. 降低逐轮日志输出频率，并比较不同工作进程数量。

一次只改变一个主要优化，确认 ID 或有序合并结果一致后再比较耗时。

## 14. 当前代码仍需留意的具体边界

这些是当前源码中的限制，不是本次已经修复的内容：

| 位置或场景 | 当前注意事项 |
| --- | --- |
| `count_chunk()` 的 `None` 分支 | `parts = chunk` 会逐字符遍历，应区分字符串与片段列表 |
| 训练使用空特殊 token 列表 | 空正则会逐字符切分；`train_bpe()` 本身也不能直接接收 `None` 后仍调用 `enumerate()` |
| 训练循环 | 没有候选时仍可能调用 `max()`，需要提前退出 |
| 固定文档分隔符 | 硬编码 `<|endoftext|>` 需要符合具体语料和特殊 token 配置 |
| 新的特殊 token | 初始化未追加缺失的词表项 |
| 任意流式片段 | 当前独立编码，不处理跨片段预分词或特殊 token |
| `from_files()` 参数 | 文件中的设置会覆盖显式传入的特殊 token |
| 直接运行文件 | 当前 main 代码位于三引号字符串内，不会执行训练 |

## 15. 如何验证自己的理解

建议保留以下小例子作为检查思路：

| 例子 | 检查目标 |
| --- | --- |
| 空输入、单个 `a` | 无候选时正常结束 |
| `aaaa` | 三个旧 pair 的计数、两次非重叠合并 |
| `abab` | 连续合并后的新邻接关系 |
| 同一个词出现多次 | 频次加权是否正确 |
| 同频的多个 pair | 训练平局规则是否正确 |
| 两条 rank 与文本位置相反的规则 | 编码是否按 rank 而不是位置或字典序选择 |
| `None` 与 `[]` | 都表示没有特殊 token，普通文本编码应一致 |
| 短特殊 token 与长特殊 token 重叠 | 在正则构造时优先匹配较长者 |
| 非 ASCII 字符、单独的不完整字节 token | 先拼字节及替换解码行为 |
| `encode_iterable()` 与整段编码比较 | 检查实际输入边界下 ID 是否一致 |

不能只检查 `decode(encode(text)) == text`：不同的分词也可能还原相同文本，还应比较 ID 序列与参考实现是否一致。

你提供过的测试输出为 22 项通过、1 项因解码缺少替换模式失败、2 项跳过。当前源码已加入 `errors="replace"`，但本文没有据此假定重跑已全部通过。macOS 上跳过内存限制测试，也不代表已经验证内存上限。
