# Section 2 知识点总结

依据：[作业 PDF](../cs336_assignment1_basics.pdf) 的 Section 2「Byte-Pair Encoding (BPE) Tokenizer」，包含 2.1-2.7，页码 3-13。以下按主题整理，每个知识点保留简短解释；UTF 编码的基本区别另参考 Unicode 官方资料。

## 一、字符与编码（2.1-2.2）

### 1. Unicode 与码点（Code Point）

Unicode 为字符提供统一的编号体系，字符的编号称为码点，通常写成 `U+XXXX`。例如 `s` 的码点是 `U+0073`；码点描述字符的身份，UTF-8 等编码则决定它如何表示为字节。

### 2. Python 的字符表示：ord、chr 与 repr

`ord()` 将单个字符转换为整数码点，`chr()` 做反向转换。`repr()` 展示便于检查的字符串表示，可能用转义形式显示不可见字符；`print()` 的显示效果不同，因此“看不见”不代表字符不存在。

### 3. 字节（Byte）与字符串（str / bytes）

一个字节由 8 个二进制位组成，取值范围是 0-255，共有 256 种可能。Python 的 `str` 表示 Unicode 文本，`bytes` 表示字节序列，遍历 `bytes` 得到的是整数；字符串的码点数量与编码后的字节数量不一定相等。

### 4. UTF-8

UTF-8 使用 1-4 个字节编码一个 Unicode 标量值，也就是除代理码点以外的码点，其中 ASCII 字符只需要 1 个字节。它适合包含大量英文的语料，也不存在多字节码元的大小端问题，但不意味着对所有语言都比 UTF-16 更省空间。[Unicode 官方说明](https://www.unicode.org/faq/utf_bom.html)

### 5. UTF-16 与 UTF-32

UTF-16 使用一个或两个 16 位码元表示一个 Unicode 标量值，即占 2 或 4 个字节；两个码元组成的表示称为代理对（surrogate pair）。UTF-32 则固定使用一个 32 位码元，即 4 个字节，因此“UTF-16 中所有字符都占两个字节”是不准确的。[Unicode 官方说明](https://www.unicode.org/faq/utf_bom.html)

### 6. 文本编码与解码（Encoding / Decoding）

`text.encode("utf-8")` 将文本转为字节，`data.decode("utf-8")` 将字节还原为文本。由于一个码点可能对应多个字节，不能假设每个字节都能单独解码；任意拼出的字节序列也不一定是合法 UTF-8。

## 二、分词方式与词表（2.2-2.3）

### 7. Token、Token ID 与 Tokenizer

Token 是分词器使用的文本单位，token ID 是它在词表中的整数编号，tokenizer 负责文本与 ID 序列之间的转换。在本作业中，普通 token 对应一个字节序列，可能是字符的一部分、子词或完整单词；token ID 与 Unicode 码点不是同一个概念。

### 8. 词级分词与字符级分词（Word-level / Character-level）

词级分词把单词作为基本单位，序列通常较短，但词表可能很大，也容易遇到未收录的词。字符级分词使用字符作为单位，粒度更细，但直接覆盖 Unicode 字符仍需要很大的词表，而且字符与字节并不等价。

### 9. 字节级分词（Byte-level Tokenization）与 OOV

纯字节级分词将编码后的每个字节作为一个 token，基础词表只需覆盖 256 种字节值。任何可用 UTF-8 编码的文本都能由这些基础单位表示，因此不会因陌生单词或字符产生词表外问题（Out-of-Vocabulary，OOV）；代价是序列往往较长。

### 10. 子词分词（Subword Tokenization）

子词分词将常见片段收进词表，让一个 token 能表示多个基础单位，例如把 `b'the'` 从三个字节 token 压缩为一个 token。它用更大的词表换取更短的序列，常见完整单词也可能成为一个 token，因此“子词”不一定严格小于一个词。

### 11. 词表大小与序列长度的权衡

细粒度分词能保持基础词表较小，却会增加模型需要处理的 token 数量，使训练更费计算，并拉长文本中的依赖距离。子词方法通过加入常见字节片段减少 token 数量，需要在词表规模和序列长度之间做取舍。

## 三、BPE 训练（2.4）

### 12. 字节对编码（Byte-Pair Encoding，BPE）

BPE 是一种反复合并高频相邻单位的算法：每轮选出出现最多的相邻 token 对，将其合并为新 token 并加入词表。虽然名字中有“字节对”，后续轮次合并的单位也可能是之前学到的多字节片段，而不只是两个原始字节。

### 13. 词表初始化与词表预算

字节级 BPE 从全部 256 个单字节 token 开始，再加入特殊 token 和训练得到的合并 token。本作业的 `vocab_size` 是最终词表大小的上限，包含上述所有部分，不能把它直接当作合并次数。

### 14. 预分词（Pre-tokenization）

预分词在 BPE 合并之前先把文本粗略切成若干片段，每个片段称为 pre-token，再将片段表示为 UTF-8 字节序列。它既限制合并范围，也便于统计重复片段；pre-token 是中间结果，仍可能被进一步表示为多个最终 token。

### 15. 正则预分词与空白保留

本作业采用 GPT-2 风格的正则表达式，按字母、数字、标点、缩写及空白等模式切分，某些片段会包含前导空格。实现中使用支持 `\p{L}`、`\p{N}` 等 Unicode 属性的 `regex` 库，`finditer()` 可逐个产生匹配，避免像 `findall()` 那样一次保存全部匹配结果。

### 16. 片段频次与相邻对计数

训练时可以先记录每种 pre-token 出现的次数，再用这个次数加权统计内部相邻 token 对。某个片段出现 10 次，其中某对在每个片段内出现 2 次，那么它对该相邻对的总计数贡献就是 20，从而无需反复扫描所有重复文本。

### 17. 合并边界与频次并列规则

BPE 只在同一个 pre-token 内合并，不跨越预分词边界；空格和标点已能作为字节表示，本作业不额外添加词尾标记。若多个相邻对频次相同，作业要求选择字典序较大的那一对，使训练结果具有确定性。

### 18. 特殊 Token（Special Tokens）

特殊 token 用来表示文档边界等元信息，例如 `<|endoftext|>`，编码时必须保留为一个具有固定 ID 的整体。训练时应先按特殊 token 分隔文本，让它们成为不能跨越的边界，并排除它们自身的合并统计；不能直接删除标记后把两侧文档拼接起来。

### 19. 训练结果：词表与合并顺序

BPE 训练输出词表 `vocab` 和有序合并列表 `merges`：本作业的词表将整数 ID 映射到字节序列，合并列表记录每一步合并的两个 token。合并的创建顺序决定后续编码时的优先级，所以保存分词器时需要同时保存词表和合并列表。

## 四、训练效率（2.5）

### 20. 并行预分词与分块边界

预分词可以把语料分给多个进程处理，再汇总统计结果。作业建议在特殊 token 所标示的文档边界处分块，避免切断本应一起处理的文本，并保证不会跨文档合并。

### 21. 增量更新相邻对计数

朴素 BPE 每轮重新扫描全部片段并统计所有相邻对，开销很大。一次合并主要影响合并位置附近的相邻关系，因此可以缓存计数并只更新受影响部分；合并轮次彼此依赖，不能像预分词那样直接独立并行。

### 22. 性能分析与缩小实验（Profiling / Downscaling）

Profiling 使用 `cProfile`、`py-spy` 等工具查明时间花在哪里，从实际瓶颈入手优化。Downscaling 则先用较小的数据集调试和验证，缩短反馈时间，但小数据集仍应尽量保留完整任务中的主要性能特征。

## 五、BPE 编解码（2.6）

### 23. 训练与编码的区别

训练根据语料中的频次学习词表和合并规则，编码则使用已经确定的规则处理新文本。编码时先处理特殊 token，再对普通片段预分词并转为字节，按训练得到的合并优先级处理相邻 token，最后映射到 ID；不会针对每段新文本重新学习高频对。

### 24. 解码顺序与非法字节处理

解码应先将各个 token ID 对应的字节拼接完整，再统一进行 UTF-8 解码，因为单个 token 不一定恰好覆盖完整字符。对词表内 ID 的任意组合也可能产生非法 UTF-8，本作业要求通过 `errors="replace"` 将非法部分替换为 Unicode 替换字符 `U+FFFD`。

### 25. 流式编码（Streaming / Lazy Encoding）

流式编码通过迭代器逐步读取文本、产生 token ID，避免把整个大文件及全部输出同时放入内存。分块时必须保留可能跨边界的分词上下文，或选择安全边界，否则结果可能与一次性编码完整文本不同。

## 六、实验与存储（2.7）

### 26. 训练语料与分词效果

不同语料的常见片段不同，因此在 TinyStories 与 OpenWebText 上训练会学到不同的词表和合并规则。将一个领域的分词器用于另一个领域时，仍然可以编码文本，但压缩效果可能变差；本作业两者的词表规模也不同，比较时需要同时考虑语料与词表大小。

### 27. 压缩比（Bytes per Token）

本作业用“原文本的 UTF-8 字节数 ÷ 编码后的 token 数”衡量压缩比，数值越大表示平均每个 token 覆盖的字节越多。它衡量的是分词后序列的紧凑程度，不等同于序列化文件的实际存储压缩比。

### 28. 吞吐量（Throughput）

吞吐量表示单位时间能处理多少文本，例如 `bytes/second`。在处理条件近似相同的前提下，可以用“总字节数 ÷ 吞吐量”估算大语料的编码时间，同时留意磁盘读取等额外开销。

### 29. 序列化与 uint16

序列化是将训练得到的词表、合并列表或编码后的 ID 保存到磁盘，供后续加载和模型训练使用。`uint16` 是取值为 0-65,535 的无符号 16 位整数，足以保存本作业 10K、32K 词表通常按连续编号生成的 ID；应检查最大 ID 是否超出范围，它与字符编码 UTF-16 没有直接关系。
