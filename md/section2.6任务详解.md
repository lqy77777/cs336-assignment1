# 第 2.6 节任务详解：BPE Tokenizer 的编码与解码

依据：项目中的 [作业 PDF](../cs336_assignment1_basics.pdf)，第 10–12 页，Section 2.6 “BPE Tokenizer: Encoding and Decoding”。同时参考 [测试文件](../tests/test_tokenizer.py) 和 [测试适配器](../tests/adapters.py)。

本文将作业要求、测试体现的要求以及实现建议分开说明，供你自己完成代码；不包含完整 Tokenizer 实现。

## 1. 这一节究竟要做什么

**用已经训练好的词表和合并规则，实现一个能将文本与 token ID 相互转换的 `Tokenizer` 类。**

作业题目是 `Problem (tokenizer): Implementing the tokenizer`，共 **15 分**。

你前面写的 `train_bpe()` 解决了“如何学习分词规则”。本节解决“如何使用这些规则处理新文本”。

```text
训练语料 → train_bpe() → vocab 和 merges
                             ↓
                       Tokenizer 实例
                             ↓
             文本 ──encode──→ token ID 列表
             文本 ←─decode── token ID 列表
```

| 对比项 | 训练阶段 | 本节的编码阶段 |
| --- | --- | --- |
| 输入 | 训练语料、目标词表大小、特殊 token | 待编码文本、已有词表和合并规则 |
| 主要操作 | 统计频次、选择最高频 pair、学习合并 | 按已有规则对文本应用合并 |
| 决定合并优先级 | 当前训练语料中的 pair 频次及平局规则 | `merges` 中的先后顺序 |
| 是否创建普通新 token | 会 | 不会 |
| 输出 | `vocab` 和 `merges` | 整数 token ID 序列 |

初始化时补充用户指定的特殊 token 是作业单独允许并要求处理的情况，与编码过程中学习普通新 token 不同。

## 2. 需要完成的接口

以下是作业推荐的接口形式。需要满足对应功能，并让测试适配器能够调用。

| 接口 | 参数 | 返回值或效果 |
| --- | --- | --- |
| `__init__(self, vocab, merges, special_tokens=None)` | 词表、合并规则、可选特殊 token | 初始化实例；`__init__` 本身返回 `None` |
| `from_files(cls, vocab_filepath, merges_filepath, special_tokens=None)` | 两个序列化文件路径、可选特殊 token | 返回一个 `Tokenizer` 实例 |
| `encode(self, text: str) -> list[int]` | 一个字符串 | 整数 token ID 列表 |
| `encode_iterable(self, iterable: Iterable[str]) -> Iterator[int]` | 可迭代的字符串来源，例如文本文件对象 | 惰性产生整数 token ID 的生成器 |
| `decode(self, ids: list[int]) -> str` | token ID 列表 | 解码后的字符串 |

补充基础概念：

- `self`：当前 Tokenizer 实例，通过它访问实例保存的词表等数据。
- `cls`：类方法接收的类，通常配合 `@classmethod` 使用，通过 `cls(...)` 构造实例。
- `Iterable[str]`：可以依次取出字符串的对象，不要求一次性存放所有字符串。
- `Iterator[int]`：可以依次取出整数的迭代器。
- `yield`：交出一个结果并暂停函数，调用方请求下一个结果时继续执行。

## 3. 初始化：理解 vocab、merges 和辅助映射

### 3.1 作业输入的数据结构

`vocab: dict[int, bytes]`：从 token ID 到字节串的映射。

```text
某个 ID → b"a"
另一个 ID → b"ab"
特殊 token 的 ID → b"<|endoftext|>"
```

`merges: list[tuple[bytes, bytes]]`：训练时按照创建顺序记录的合并对。

```text
[(b"a", b"b"), (b"ab", b"c")]
```

这里每项仍然是两个 token，不能只保存拼接后的 `b"ab"` 或 `b"abc"`。列表的顺序也必须保留。

`special_tokens: list[str] | None`：需要作为整体识别的特殊字符串。与当前训练函数中的非空假设不同，本节接口允许它是 `None`；实现时也要合理处理空列表。

### 3.2 建议建立的辅助结构

| 结构 | 方向 | 用途 |
| --- | --- | --- |
| 原始词表 | `ID → bytes` | 解码时查找字节串 |
| 反向词表 | `bytes → ID` | 编码结束后查找 token ID |
| 合并优先级表 | `(bytes, bytes) → rank` | 快速判断一个 pair 能否合并、优先级是多少 |
| 特殊 token 映射 | `str → ID` | 直接编码特殊字符串 |

`rank` 可以使用合并规则的列表索引：第一条是 `0`，第二条是 `1`。**rank 越小，越先应用。**

可以先思考：如果词表中包含 `b"abc"`，是否就应该贪心匹配最长字符串？不应该；是否以及何时得到它，仍要遵守训练时的合并顺序。

### 3.3 补充特殊 token

作业明确要求：用户指定的特殊 token 如果尚未在词表中，应该追加到词表。

建议步骤：

1. 将特殊字符串编码为 UTF-8 字节串。
2. 检查这些字节是否已经有对应 ID。
3. 已存在时复用 ID，未存在时分配新的 ID。
4. 同步更新反向映射和特殊 token 映射。

实现建议：复制传入的词表再补充，避免意外修改调用者的数据；新 ID 可从已有最大 ID 加一开始，不要把“字典长度”等同于“最大 ID 加一”。

## 4. encode：将文本转成 token ID

### 4.1 完整处理顺序

1. 识别特殊 token，保留普通文本和特殊 token 的原始顺序。
2. 对普通文本使用与训练时一致的 `PAT` 预分词。
3. 将每个预分词编码为 UTF-8，并拆成单字节 token 序列。
4. 在各个预分词内部按 `merges` 的优先级合并。
5. 用反向词表将最终 token 字节串转换为 ID。
6. 特殊 token 直接输出其整体 ID。
7. 按文本顺序返回一个 `list[int]`。

**不能跨预分词边界合并，也不能跨特殊 token 边界合并。**

### 4.2 编码阶段如何决定合并哪个 pair

编码时不需要重新统计全语料频次，也不再选择当前文本中出现次数最多的 pair。

对当前预分词：

1. 查看所有相邻 pair。
2. 找出在合并优先级表中存在的候选。
3. 选择 rank 最小的候选。
4. 从左到右合并该 pair 的非重叠出现位置。
5. 更新序列，重复以上过程，直到没有规则可用。

初学时可以先实现清晰的版本，再考虑缓存或更高效的候选维护；最大堆不是本节的强制要求。

### 4.3 作业示例：the cat ate

作业给出的教学词表如下。它是简化示例，不是包含全部 256 个基础字节的完整词表。

| ID | token 字节串 | ID | token 字节串 |
| ---: | --- | ---: | --- |
| 0 | `b" "` | 6 | `b"th"` |
| 1 | `b"a"` | 7 | `b" c"` |
| 2 | `b"c"` | 8 | `b" a"` |
| 3 | `b"e"` | 9 | `b"the"` |
| 4 | `b"h"` | 10 | `b" at"` |
| 5 | `b"t"` | | |

合并规则依次为：

```text
rank 0：(b"t", b"h")
rank 1：(b" ", b"c")
rank 2：(b" ", b"a")
rank 3：(b"th", b"e")
rank 4：(b" a", b"t")
```

输入 `"the cat ate"`，预分词结果是：

```text
["the", " cat", " ate"]
```

每个预分词独立处理：

| 预分词 | 合并过程 | 最终 ID |
| --- | --- | --- |
| `"the"` | `[t,h,e] → [th,e] → [the]` | `[9]` |
| `" cat"` | `[空格,c,a,t] → [空格+c,a,t]` | `[7,1,5]` |
| `" ate"` | `[空格,a,t,e] → [空格+a,t,e] → [空格+at,e]` | `[10,3]` |

因此最终输出为 `[9, 7, 1, 5, 10, 3]`。

注意第二、第三个预分词的前导空格不能删除；删除后就无法还原原文，ID 也会改变。

### 4.4 自测合并优先级

假设只有以下规则：

```text
rank 0：(b"b", b"c")
rank 1：(b"a", b"b")
```

对于 `[b"a", b"b", b"c"]`，应先合并 `(b"b", b"c")`，得到 `[b"a", b"bc"]`，即使 `(b"a", b"b")` 在文本中出现得更靠左。

## 5. 特殊 token：训练和编码时的处理不同

训练普通 BPE 规则时，你把特殊 token 分隔出去，不让它参与普通 pair 统计。

**编码时不能把特殊 token 丢掉。它需要变成一个独立 ID，并占据原来的位置。**

例如：

```text
输入：hello<|endoftext|>world

输出：hello 的 ID 序列 + [特殊 token ID] + world 的 ID 序列
```

实现时应注意：

- 不能直接沿用丢弃分隔符的 `re.split()` 结果，否则特殊 token 会消失。
- 特殊字符串进入正则前需要转义，防止其中的 `|`、括号等被解释为正则语法。
- 按特殊 token 分隔前后，所有空白和换行都要保留。
- 特殊 token 已经在词表中时，不应再创建重复 ID。
- 特殊 token 不在词表中时，按照初始化规则追加。

### 重叠特殊 token

当前测试 `test_overlapping_special_tokens` 同时提供：

```text
<|endoftext|>
<|endoftext|><|endoftext|>
```

当文本中出现后一种连续字符串时，测试要求将它保留为一个整体 token。也就是在同一位置有多个可匹配特殊 token 时，优先匹配更长者。

实现建议：构造正则分支前先按特殊字符串长度降序排序。这里是特殊 token 的匹配策略，不是把普通 BPE 改成最长匹配。

## 6. decode：将 token ID 转回文本

### 6.1 作业要求的顺序

1. 根据每个 ID 查到对应的字节串。
2. 按原顺序拼接所有字节串。
3. 将拼接结果按 UTF-8 解码。
4. 遇到非法 UTF-8 字节时，使用 Unicode 替换字符 `U+FFFD`，即常见的 `�`。

先理解下列片段中的参数、变量和返回值：

- `ids`：待解码的 ID 列表。
- `vocab[token_id]`：当前 ID 对应的 `bytes`。
- `raw`：全部 token 字节拼接后的结果。
- `text`：UTF-8 解码后的字符串，应作为 `decode()` 的返回值。

```python
raw = b"".join(vocab[token_id] for token_id in ids)
text = raw.decode("utf-8", errors="replace")
```

第一行逐个查词表并拼接字节；第二行统一解码，遇到非法字节时替换。

### 6.2 为什么不能逐个 token 解码再拼字符串

一个 Unicode 字符可能由多个 token 的字节共同组成。

例如，“你”的 UTF-8 字节为：

```text
E4 BD A0
```

如果三个字节分别属于不同 token，单独解码每个 token 都是不完整的 UTF-8；先拼接再解码才能恢复“你”。

因此，`decode([id1]) + decode([id2])` 不保证等于 `decode([id1, id2])`。

### 6.3 非法字节与不存在的 ID 是不同问题

作业明确要求用 `errors="replace"` 处理的是：ID 存在，但它们对应的字节拼接后不构成合法 UTF-8。

如果 ID 根本不存在于词表，属于词表查找错误，不会因为设置了 `errors="replace"` 自动解决。不要将两个概念混淆。

## 7. encode_iterable：大文件的流式编码

### 7.1 为什么不能直接调用一次 encode

对整个文件先 `read()`，再调用 `encode()`，会同时保存大量文本和 token ID。内存随文件大小增长。

作业要求 `encode_iterable()` 惰性地产生 ID。处理完可以确定的内容后逐个 `yield`，不把整份输入和全部输出积累在函数内部。

调用方如果自己执行 `list(tokenizer.encode_iterable(...))`，仍会保存全部结果；这是调用方的内存选择，不代表生成器应该提前构造完整列表。

### 7.2 仅仅加上 yield，并不能解决分块边界问题

假设输入来源先提供 `"hel"`，再提供 `"lo"`。分别编码这两个片段，可能不同于一次编码 `"hello"`。

原因是：完整的 `hello` 可能在词表中对应一个 token，但片段边界阻止了它的形成。

特殊 token 也可能跨片段，例如前一段结束于 `"<|endof"`，后一段开始于 `"text|>"`。

因此，对同一段连续文本，流式处理的目标应是：在合理的边界约定下，得到与整段编码一致的 ID，而不只是解码后字符碰巧相同。

### 7.3 如何思考安全边界

作业第 11 页明确提醒，分块不能截断 token，否则会改变分词结果。实现建议：

1. 明确输入片段是独立文档，还是同一文本流的连续片段。
2. 连续文本流需要保留尚不能确定的尾部，等待后续输入再处理。
3. 只输出已经确认不会受后续文本影响的部分。
4. 流结束时处理剩余缓冲区。
5. 不要将 `strip()` 或删除换行当成处理边界的方法。

测试使用文件迭代按行输入，但这不意味着任意字符串片段都可以独立编码。尤其需要检查 `PAT` 对连续空白、尾部空白的匹配，以及跨行的用户特殊 token。应验证实际边界策略，而不是仅凭换行就认定安全。

关于“常量内存”：作业目标是不让工作内存随整个文件大小增长；词表、当前块及必要尾部仍需要内存。对于任意长且不可安全切分的片段，不能无条件承诺固定缓冲上限；若采用缓存，也应限制缓存大小。

## 8. from_files：加载训练产物

这是类方法，不是重新训练的入口。

参数：

- `vocab_filepath: str`：序列化词表文件路径。
- `merges_filepath: str`：序列化合并规则文件路径。
- `special_tokens: list[str] | None`：需要作为整体处理的特殊字符串。

返回值：一个初始化完成的 Tokenizer 实例。

处理顺序：读取两个文件 → 还原正确的数据类型和顺序 → 调用构造函数 → 返回实例。

作业要求它与你训练代码的输出格式一致，没有在这一节强制统一为某一种自定义保存格式。需要注意：

- `bytes` 不能随意当成普通 UTF-8 字符串保存，有些 token 字节本身不构成完整字符。
- 如果用 JSON，需要明确字节串的可逆表示，例如整数列表或十六进制字符串。
- JSON 对象的键通常是字符串，读回词表后要恢复整数 ID。
- 合并规则必须保留列表顺序，并恢复为两个字节串组成的 pair。
- 本地测试 fixture 使用其自己的格式；查看测试加载辅助函数，避免将它与自己保存的格式混为一谈。

你上一次计时运行只保存了日志和耗时，未保存词表与合并规则。要使用 `from_files()`，需要先准备这两个训练产物；但可以先用手工小词表或测试提供的数据开发编码、解码功能，不必每次都重新训练大语料。

## 9. 测试要求与运行方式

作业要求实现 `tests/adapters.py` 中的 `get_tokenizer()`，让它根据传入的词表、合并规则和特殊 token 返回你的 Tokenizer 实例，然后运行：

```bash

```

这条命令应在项目根目录执行。本次整理文档没有修改适配器或运行测试。

当前测试主要检查：

| 测试方向 | 要验证的行为 |
| --- | --- |
| 空字符串与单字符 | 空输入返回空 ID 列表，基本字符正常处理 |
| Unicode | 中文、其他非 ASCII 文本能正确往返 |
| 与 tiktoken 比较 | 使用对应参考词表时，ID 序列与参考实现一致 |
| 特殊 token | 保持整体、不遗漏、不破坏相邻文本 |
| 重叠特殊 token | 同一起点优先识别较长特殊字符串 |
| 空白与换行 | 特殊 token 附近的换行等内容原样保留 |
| 流式编码 | 文件逐步编码的结果正确，并与参考结果一致 |
| 内存 | `encode_iterable()` 避免一次性载入所有数据 |

“可以往返还原文本”不是全部标准：错误的分词也可能还原出原文，但 ID 序列与参考实现不同。

当前内存限制测试带有平台条件，在非 Linux 系统（例如你的 macOS）上会跳过。看到跳过不能当作内存性能已通过验证。普通 `encode()` 的内存测试还被标记为预期失败，应结合测试标记理解输出。

## 10. 建议实现顺序

以下是学习和开发建议，不是作业强制顺序：

1. **初始化数据结构**：词表、反向词表、合并 rank、特殊 token 映射。
2. **先实现 decode**：通过字节拼接理解 token 与 Unicode 字符的关系。
3. **实现单个预分词的合并**：先用小例子验证 rank 和非重叠合并。
4. **实现普通文本 encode**：串起正则预分词、字节转换、合并和 ID 查找。
5. **加入特殊 token 支持**：检查保留顺序、缺失时追加、长短重叠和换行。
6. **实现 from_files**：验证保存再加载后编码结果相同。
7. **实现 encode_iterable**：重点设计惰性输出和安全边界。
8. **接入 get_tokenizer 并运行测试**：再根据失败类型定位问题。

先完成正确版本，再考虑对重复预分词的编码结果做有界缓存，减少重复应用合并规则；不要让无限增长的缓存破坏流式内存目标。
